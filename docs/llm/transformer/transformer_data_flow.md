# 学Transformer先别看公式：先看懂数据怎么流动的

上一篇[为什么大模型常用 Transformer](./transformer_base_1.md)讲了它的优势：让序列里的位置直接交换信息，训练时还能并行计算。但拿到一句话，它到底怎么变成模型输出？

录友面试时可能会被问：“输入一段文本，到生成下一个 Token，中间经过了什么？每一步的数据形状是什么？”

“先 Embedding，再 Attention，最后 FFN。”这几个名字没错，但漏了编号怎么变成向量、输出怎么变回 Token。只记模块名，看代码时就容易把词表大小当成隐藏维度，或者以为每过一层就多生成一个字。

这篇只跟一条线：**文本进入模型，变成向量，经过多层更新，最后预测下一枚 Token。** 为了讲清生成过程，下面采用 GPT 这类 **Decoder-only 自回归语言模型**，不把所有 Transformer 架构混在一起。

## 简要回答

- **Tokenizer 分词并编号**：文本变成 Token ID 序列；编号本身还不是语义向量。
- **Embedding 查表**：每个编号取出一个向量，并在模型计算中引入位置信息。
- **多层 Block 更新表示**：Attention 汇聚允许访问的上下文，FFN 对每个位置分别加工，残差连接和归一化帮助信息稳定传递。
- **输出头预测下一枚 Token**：用最后位置的表示给词表候选打分，经 Softmax 和解码策略选出一枚，再接回上下文继续计算。

**Block 里反复变化的是向量内容；生成循环里不断增长的是序列长度。**

## 一句话进来，为什么先变成编号？

用“小猫在”作例子。为便于画图，**假设**分词结果是 `[小, 猫, 在]`，对应编号 `[12, 35, 8]`。这些编号是演示值，不对应真实词表。

实际怎么切，由 Tokenizer 的规则和词表决定。一个 Token 可能是一个字、一个词的一部分，或其他文本片段，不能直接说“大模型每次生成一个汉字”。

接下来统一假设：只处理一条序列，长度 `L=3`，隐藏维度 `d=512`，词表大小 `V=10000`。下面省略批次维度；真实代码里通常还会有一维批次大小 `B`。

Embedding 可以理解成一张 **10000 行、512 列的可训练查找表**。每行对应一个 Token ID，每行存着 512 个数。输入三个编号，就取出三行，得到 `3 × 512` 的矩阵。

**10000 是能编号的 Token 种类数，512 是每个位置的表示宽度。** ID 为 35，不代表向量有 35 维；512 维也不代表词表只有 512 个 Token。

这张图回答的是：同一段文本在模型里依次变成了什么？三个编号从 Embedding 表取出三行向量，经过多层 Block 后仍对应三个位置；最后取末尾位置的表示，交给输出头预测下一枚 Token。

## 向量有了，模型怎么知道顺序？

单靠 Embedding 查表，“小猫在”和“在猫小”只是同几行向量换了顺序。标准自注意力本身缺少明确的位置依据，需要额外引入位置信息。

经典 Transformer 会把位置编码加到输入向量上；也有模型使用 RoPE（旋转位置编码），在 Attention 内对 Q、K 做位置相关变换。**不能把所有模型都画成“Embedding 后统一加一次位置向量”。**

这篇只记一件事：位置信息参与后续计算，使模型能利用先后和距离关系。它通常不会给矩阵额外加一列，我们跟踪的表示仍是 `3 × 512`。具体机制见[位置编码](./pos_encode.md)。

## 一个 Block 里，哪些数据在互相影响？

进入 Block 的不是汉字，也不是 Token ID，而是每个位置当前的向量表示。这里先看 Attention 和 FFN 的分工，完整组件顺序可对照[一层 Transformer Block](./transformer_structure.md)。

**Attention 做跨位置的信息汇聚。** 计算“在”这个位置时，它可以根据当前表示，对“小”“猫”和自身分配不同权重，再把相应信息聚合回来。

但 Decoder-only 模型有因果掩码：第一个位置不能看第二、第三个位置，第二个只能看自己和第一个。**能访问哪些位置，先由掩码限制；对可见位置分配多少权重，再由注意力计算决定。**

多头注意力会并行计算多组这样的关系，再合并并投影回隐藏维度。我们跟踪的主干输出仍是 `3 × 512`，但每行已经结合了可见上下文。Q、K、V 的具体角色见[Attention 到底在干嘛](./qkv.md)。

**FFN（前馈网络）做逐位置的非线性加工。** 在一个简单的两层 FFN 例子里，三个位置都先从 512 维升到 2048 维，经过激活函数，再回到 512 维：

```text
3 × 512 → 3 × 2048 → 激活 → 3 × 512
```

同一层 FFN 的参数由各位置共享，但它不会在这里直接把第一个位置和第三个位置混合。跨位置的交流主要由 Attention 完成，FFN 加工的是各位置已经拿到的信息。2048 是示例中间维度，不是所有模型的固定配置。

![因果注意力与逐位置加工](https://file1.kamacoder.com/i/web/20261020133642.png?v=20261005)

这张图回答的是：Attention 和 FFN 的“加工方向”有什么不同？Attention 的连线跨越位置，并受到因果掩码限制；FFN 的三条路径各自加工，输出仍与原位置一一对应。

Block 里还有两件事：**残差连接把子层输入与输出相加**，保留直接的信息传递路径；**归一化调节数值尺度**，帮助训练更稳定。它们都不增加 Token 数，残差相加也要求两路形状兼容。

归一化可以放在子层前或后，模型也可能采用 LayerNorm 或 RMSNorm。这里不强行套一个固定顺序。还要纠正一个误区：**Attention 包含 Softmax 等非线性操作，并不是“前面全是线性，直到 FFN 才有非线性”。**

## 为什么堆了很多层，还是三个位置？

在这个例子里，每个 Block 都接收 `3 × 512`，输出 `3 × 512`，所以能一层接一层地串起来。形状相同不代表内容没变，每一层都在更新表示；不同层通常也有各自的参数。

“小”依然占第一行，“猫”依然占第二行，但行里的数值已经不是最初查表得到的那一组。最后一行表示的是模型处理过“小猫在”这段上下文后的当前状态。

**堆 24 层不会把三个 Token 变成 24 个 Token。** 层数决定经过多少次变换，序列长度决定有多少个位置，这是两个维度。

## 最后一个向量，怎么变成下一枚 Token？

在模型规定的最终归一化等处理后，取最后位置的 `1 × 512` 表示，经过输出头映射为 `1 × 10000` 的 logits。logits 就是词表中各候选的原始分数，还不是概率。

Softmax 把它们转换成概率分布。假设“睡”“跑”“吃”都有一定概率，接下来由**解码策略**决定选谁：贪心解码取最高分，采样则按调整后的分布抽取，所以不是每次都选最高分。

假设这次选中“睡”，就把它的 ID 接到原序列末尾。下一步的逻辑上下文变成“小猫在睡”，再预测后面的一枚。遇到结束 Token 或达到生成限制等停止条件，循环结束。

这张图回答的是：一次预测为什么只让序列增长一枚 Token？末尾向量产生候选分数，解码策略选出一个 ID；这个 ID 回到输入序列，成为下一步可使用的上下文。

从逻辑上看，每次都在使用增长后的上下文。实际推理常用 **KV Cache** 缓存历史位置在各层的 K、V，后续步骤主要计算新位置，避免每一步把整个前缀重复算一遍。缓存改变计算复用方式，不会消除“先得到这一枚，才能预测下一枚”的依赖。

## 看代码时，先查哪几个形状？

遇到维度对不上，先标出 `B、L、d、V`，沿主干检查这四个位置：

| 检查点 | 常见形状 | 这一维在表示什么 |
|---|---|---|
| Token ID | `[B, L]` | 每条序列有多少个编号 |
| Embedding 输出 | `[B, L, d]` | 每个位置取出一个向量 |
| Block 主干输出 | `[B, L, d]` | 位置数和宽度保持，内容更新 |
| 全位置输出头 | `[B, L, V]` | 每个位置给词表候选打分 |

生成下一枚时只需要末尾位置的分数，推理实现可以只算这部分输出头。别看到词表维度很大，就先改 Embedding 宽度：两者承担的职责不同。

如果只是加长输入，先增长的是 `L`，每行宽度 `d` 不会跟着增长。但更长的序列会增加计算和缓存压力，“形状能对上”并不代表显存就够用。

## 面试官继续追问，怎么答？

**问：输入 Embedding 相同，为什么最终表示不同？**

同一个 Token ID 查到的初始向量相同，但所处位置、可见上下文不同，经过各层计算后的表示就可以不同。查表结果和上下文表示不是一回事。

**问：既然生成只用最后位置，训练为什么要算多个位置？**

训练文本已知，可以把目标错开一位，让多个位置分别预测各自的下一枚 Token，再一起计算损失。例如输入“小、猫、在”，对应目标可以是“猫、在、睡”。因果掩码防止位置偷看未来，单个位置能看到自身输入。

**问：模型输出的是字，还是编号？**

输出头给词表候选打分，解码策略选出 Token ID，再由 Tokenizer 解码为文本。一个 Token 不一定是一个完整汉字或单词。

**问：所有 Transformer 都按这个方式生成吗？**

不是。这里跟踪的是 Decoder-only 自回归语言模型。Encoder-only 常输出上下文表示，Encoder-Decoder 还涉及编码器输出和交叉注意力。区别见[Transformer 三种架构](./transformer_base_encoder_decoder.md)。

录友先拿“小猫在”走一遍：编号在哪一步变成向量，哪里交换上下文，哪里选出新 Token。能把每条箭头两端的数据讲明白，再看公式就有落点了。
